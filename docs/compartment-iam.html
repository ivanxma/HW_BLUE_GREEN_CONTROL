HeatWave Blue Green · VM 132.145.60.181 · uk-london-1

What caused the original warning

The earlier regional membership check tried to list blue-green deployments in every visible compartment. Instance principals can see compartment names without having MySQL access in those compartments. Read-only probes succeeded in HWDemo (11 deployment records) and returned 404 NotAuthorizedOrNotFound in the tenancy root and ADB. The original request ID alone does not distinguish authorization from a missing resource; the reproduced compartment-specific responses indicate an access boundary.

The application now queries only the selected compartment. No MySQL permission outside it is assumed. Outside-compartment discovery is disabled and does not block creation inside the selected compartment. If the selected compartment itself is inaccessible, the dashboard shows a warning and an IAM example targeting that compartment.

1. Match only this VM

Create or reuse a dynamic group, for example heatwave-bluegreen-vm, with this rule:

ALL {instance.id = 'ocid1.instance.oc1.uk-london-1.anwgiljteicj2tickfpar7mvn26wgilwfjhvlgeagtw5nfsn7bpaeoryd7ma'}

Use the actual dynamic-group name in the policies. If your identity-domain setup requires a domain-qualified name, use the group reference shown by your OCI identity administrator.

2. Grant discovery in HWDemo only

Create the policy in HWDemo, or an ancestor with authority to grant access to HWDemo:

Allow dynamic-group heatwave-bluegreen-vm to read mysql-family in compartment id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra

This confines MySQL observation to that compartment. The app does not require an additional tenancy-wide MySQL grant. An instance principal's built-in compartment inspection can populate the compartment selector; visibility in that selector does not imply permission to read MySQL resources there.

3. Optional live operation permissions in HWDemo

Only when creation, HA changes, channel changes and switchover are intended, grant MySQL management in the same compartment:

Allow dynamic-group heatwave-bluegreen-vm to manage mysql-family in compartment id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra

Allow dynamic-group heatwave-bluegreen-vm to manage secrets in compartment id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra
Allow dynamic-group heatwave-bluegreen-vm to read vaults in compartment id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra
Allow dynamic-group heatwave-bluegreen-vm to use keys in compartment id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra

Provisioning also requires the relevant subnet and NSG attachment permissions documented by Oracle. If network or Vault resources are in another compartment, request access to that specific compartment separately. The console does not grant policies or expand permissions automatically. This guide does not claim that live provisioning permissions have been validated.

4. Changing compartment

If a user chooses another compartment and receives an access warning, copy the policy example shown in the dashboard. Its in compartment id value will be the newly selected compartment. An administrator can approve access for that compartment, or the user can return to an authorized compartment. The app never substitutes a tenancy-wide grant.

All non-deleted DB-system states are shown by default. Read replicas remain visible and prevent blue-green creation until removed; a replica in DELETING or FAILED state still counts as present. A failure to inspect replicas also prevents creation because support eligibility is unknown.

Registrations moved to other compartments are outside this view. Known registrations in the selected compartment are excluded; OCI validates source conflicts outside the visible scope when creation is submitted. Review that scope limit before performing HA or event changes.

5. Verify only the authorized compartment

cd /home/opc/heatwave-bluegreen
.venv/bin/python diagnose_discovery.py validation/compartment-check.json \
  --compartment-id ocid1.compartment.oc1..aaaaaaaaro5p36bcnkt2zhz5uu3z265tr5fo5ldquih473zgyvwf6dpye5ra

After IAM propagation, refresh the dashboard. The application has no regional-discovery cache to clear. Keep BLUEGREEN_OCI_READ_ONLY=1 while validating. The console continues to use the instance principal; no user API keys or OCI configuration file are required.

If listing still returns 404 in the authorized selected compartment, check the dynamic-group rule, region, compartment OCID and any policy conditions. Provide that operation's current request ID to your IAM administrator or Oracle Support. Oracle's published MySQL IAM tables do not yet enumerate every blue-green API, so the documented mysql-family grant must be confirmed against the actual service response.
